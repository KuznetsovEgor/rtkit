# Публичный demo-профиль CRM

Изолированный Compose-профиль для отдельного VPS. Он не использует локальный `infra/docker-compose.yml`: опубликованы только порты HTTPS proxy `80/443`; Postgres и Keycloak доступны сервисам через внутренние сети. CMS/LMS mock запускаются рядом с API в одном контейнере и слушают только loopback API-контейнера.

## Подготовка VPS

Нужны Docker Engine с Compose v2 и DNS A/AAAA записи трёх хостов на VPS. Разрешите входящие TCP 80 и 443 (UDP 443 опционален для HTTP/3). Не публикуйте порты БД, API или Keycloak отдельно. TLS сертификаты Caddy получает и продлевает автоматически.

В каталоге `crm/deploy/public-demo`:

```sh
cp .env.example .env
openssl rand -hex 32 # выполнить отдельно для POSTGRES_PASSWORD
openssl rand -hex 32 # выполнить отдельно для KC_BOOTSTRAP_ADMIN_PASSWORD
chmod 600 .env
```

Сгенерируйте два разных значения и внесите их в пустые поля `.env`; используйте только hex, чтобы строка подключения PostgreSQL оставалась безопасной для URL. Compose завершится с ошибкой, пока поля пусты. Домены должны соответствовать реальным DNS записям. Realm для публичного входа соберётся при Docker build из отдельной HTTPS-конфигурации; синтетические учётные записи создаются отдельным шагом ниже.

Запуск и просмотр состояния:

```sh
docker compose --env-file .env up -d --build
docker compose --env-file .env ps
docker compose --env-file .env logs -f proxy api keycloak
```

Откройте `https://crm.futura.team`. Документация API: `https://api.crm.futura.team/docs`; административный вход Keycloak: `https://auth.crm.futura.team/admin/`. Администратор Keycloak задаётся только переменными окружения. Demo realm не импортирует пользователей или пароли.

## Публичная демо-форма заявок

После сборки откройте `https://crm.futura.team/request/`. Одноэкранная форма предлагает три потока: заявка вуза, B2B/корпоративное обучение и физлицо. Текст страницы прямо требует использовать синтетические данные и не вводить настоящие контакты. API включён только Compose профилем публичного демо; при выключенном `PUBLIC_DEMO_INTAKE_ENABLED` маршрут недоступен.

При отправке API валидирует поля, проверяет скрытое honeypot-поле, ограничивает отправки до пяти на доверенный IP за 15 минут, дедуплицирует повторы по ключу идемпотентности и по одинаковой форме за 24 часа. Создание контакта, организации для заявки вуза или B2B, CRM-активности, события истории и записи дедупликации проходит в одной транзакции. B2B создаёт корпоративную активность, связанную с организацией сегмента `company`; заявка вуза создаёт организацию сегмента `university`; физлицо создаётся без организации. Новая заявка назначается первому активному демо-КАМ из `kam_directory`; seed создаёт только синтетические аккаунты. Миграция `0032_public_demo_intakes.sql` уже хранит ключи/отпечатки заявок и ссылается на обычные активности, поэтому отдельная схема БД для третьего типа не нужна. Контакты хранятся в CRM как обычная запись, поэтому использовать можно только вымышленные данные.

Проверка выпуска после обновления checkout:

```sh
docker compose --env-file .env up -d --build
docker compose --env-file .env ps
```

Миграция `0032_public_demo_intakes.sql` применяется при запуске API. После одноразового provisioning учёток войдите как `kam.anna`, откройте очередь и отправьте вымышленный запрос на `/request/`; новая активность должна появиться у КАМ с пометкой `Демо` в названии. Откройте её историю, чтобы увидеть текст запроса и событие о публичной demo-странице. Роль `admin` без `manager` по-прежнему не имеет доступа к бизнес-очереди CRM; для проверки как администратор используйте только учётку с обеими ролями. Никаких действий на VPS эта инструкция не выполняет.

Форма создаёт CRM-запись непосредственно на демонстрационном стенде. Это не интеграция и не канал приёма заявок реальной РТК, CMS или LMS. Rate limit хранится в памяти одного процесса API и рассчитан на текущую одноэкземплярную демо-конфигурацию; при горизонтальном масштабировании его нужно перенести в общее хранилище.

## Однократное создание синтетических учёток

Для уже развёрнутого стенда с четырьмя учётками и для наполнения трёх процессов используйте [защищённый сценарий public seed](../../scripts/public-demo-seed.md). Он отдельно проверяет существующую БД, сохраняет прежние записи и требует явных флагов перед изменениями.

После первого запуска стека API применит миграции базы. Затем в каталоге `crm/deploy/public-demo` создайте закрытый каталог и запустите одноразовый контейнер provisioner:

```sh
install -d -m 700 .private-demo-credentials
DEMO_UID="$(id -u)" DEMO_GID="$(id -g)" docker compose --env-file .env --profile provision run --rm demo-provisioner
```

Контейнер подключён только к внутренней сети Compose. Он создаёт `kam.anna` (КАМ), `kam.dmitry` (КАМ), `manager` (руководитель) и `admin` (администратор) с синтетическими именами из локальной таблицы известных пользователей. Пароли генерируются криптографическим генератором при запуске, в CRM записываются роли и оба КАМ добавляются в каталог назначения. Файл `.private-demo-credentials/demo-accounts.txt` создаётся на VPS с правами `600`, принадлежит пользователю, запустившему команду, и игнорируется Git. Сохраните его в закрытом месте и удалите с VPS после защищённой передачи учётных данных.

Запуск намеренно откажется перезаписывать файл или сбрасывать уже существующую учётную запись. Provisioning меняет Keycloak и таблицы доступа CRM; при частичной ошибке сохраните файл, проверьте четыре аккаунта и `known_crm_users`/`kam_directory` перед любым ручным восстановлением. Не публикуйте содержимое файла и не добавляйте его в резервные копии с общим доступом.

Данные Postgres, закрытые файлы CRM и состояние mock, а также сертификаты Caddy сохраняются в именованных volumes. Резервируйте Postgres штатным `pg_dump` и сохраняйте защищённую копию volume `app_data`; сертификаты можно восстановить через Caddy. `docker compose down` сохраняет volumes. `docker compose down -v` удаляет все данные и сертификаты.

Перед первым входом проверьте наличие четырёх синтетических записей в Keycloak и соответствующих ролей `admin`, `manager`, `kam`. Пользовательские каталоги/учебные факты приходят только из синтетических локальных mock; подключение реальных CMS/LMS не настроено. Этот профиль готовит конфигурацию, но не меняет DNS, firewall и сервер и сам по себе не доказывает, что текущие сборки приложения прошли полноценный security review.
