# RTK CRM — локальный рабочий срез

Рабочий вертикальный срез CRM на React + TypeScript, Fastify, Drizzle ORM, PostgreSQL и Keycloak OIDC. Данные стенда полностью синтетические. Внешние интеграции реализованы как явно обозначенные локальные HTTP mock-сервисы; реальные системы заказчика не подключены. B02 добавляет локальные проектные инструкции и контекстную подсказку, B03 — портфель открытых активностей для руководителя, B04 — контрольные состояния пунктов партнёрства с вузом, B05 — индивидуальный маршрут и учёт готового заказа, B06 — компактный план корпоративной программы, B07 — вложения в активности, B08 — серверный импорт контактов, поставщиков и внешних индивидуальных заявок, B09 — двусторонние CMS/LMS mock-обмены с очередью, журналом, повтором и read-only проекцией, B10 — готовые отчёты, B11 — выбор колонок выгрузки, B12 — хранение строк отчёта в PostgreSQL и серверную пагинацию без предела в 20 000 строк. A07–A09 добавляют администрирование общей схемы вузов с предпросмотром переноса активностей и проверку ревизии схемы при переходе.

Локальный API по умолчанию слушает только `127.0.0.1`; его OpenAPI использует текущий адрес сайта и не закрепляет `localhost` в контракте. Скрипт настройки Keycloak синхронизирует разрешённый адрес возврата клиента `lct-web` из `WEB_ORIGIN`: для локального HTTP допустим только loopback, для внешнего адреса требуется HTTPS. Локальный Compose использует `start-dev` и не предназначен для публикации простым пробросом портов. Отдельный [публичный профиль](deploy/public-demo/README.md) развёрнут на российском VPS с HTTPS: [CRM](https://crm.futura.team/) и [форма синтетических заявок](https://crm.futura.team/request/). Это демонстрационный стенд, а не подтверждение нормативного соответствия или подключение к системам заказчика.

Короткая карта компонентов и потоков данных: [архитектура](docs/ARCHITECTURE.md); смысл трёх процессов, ролей и метрик: [продуктовая модель](docs/PRODUCT.md); границы локальных CMS/LMS mock и импорта: [интеграции](docs/INTEGRATIONS.md). Соответствие десяти ключевых кадров Gate B и текущего интерфейса зафиксировано в [карте дизайна](docs/DESIGN.md). Фактические проверки и открытые критерии A01–A34 собраны в [реестре качества](docs/QUALITY.md).

Публичный стенд — актуальная точка проверки решения. [Пакет ZIP от 28 сентября](delivery/RTK_CRM_jury_bundle_20260928.zip), [DOCX](delivery/RTK_CRM_delivery_r08.docx) и [PPTX](delivery/RTK_CRM_owner_review_A53_20260928_r10.pptx) сохранены как исторические материалы: они не отражают все последующие функции и проверки и не являются финальной сдачей по официальному шаблону презентации. [Архив исходников локального стенда](delivery/RTK_CRM_source_local_20260928.zip) также относится к этой дате. Текущие результаты и открытые проверки ведутся в [реестре качества](docs/QUALITY.md) и Git-ignored `.agent/BACKLOG.md`; [источник архитектурной схемы ArchiMate Open Exchange XML](delivery/lct-crm-architecture-open-exchange.xml) доступен отдельно. CMS/LMS остаются локальными mock, XML прошёл XSD-валидацию, но импорт в Archi ещё не проверен.

Новый пакет добавляет сквозную ленту действий команды с фильтром по автору-КАМ и личную ленту КАМ. В карточке задачи можно записать обновление и подписаться на уведомления внутри CRM; завершение и обновления доставляются подписчикам кроме автора. У руководителя есть командный дашборд, у КАМ — показатели его открытых доступных активностей. Светлая/тёмная тема переключается в верхней панели. CSV UTF-8 теперь принимается для контактов, поставщиков и индивидуальных заявок через прежние предпросмотр и подтверждение; готовые отчёты можно выгрузить в CSV из сохранённого среза. Выгрузка защищает табличные ячейки от интерпретации как формул. Живой визуальный и клавиатурный QA этих дополнений ещё не выполнен из-за ограничения браузерного инструмента.

Руководитель может передать одну активность другому действующему КАМ через предпросмотр последствий и отдельное подтверждение. Открытые задачи переходят новому ответственному с прежними сроками; выполненные задачи, стадия, исходы и старая история сохраняются. Прежний КАМ теряет доступ к карточке, файлам и ранее созданному отчёту после передачи. Личные импортированные записи не передаются. Список КАМ синхронизируется при запуске из тестового Keycloak. A10 позволяет администратору включать и отключать доступ известных пользователей CRM с обязательной причиной и аудитом; отключение действует на каждый новый API-запрос, включая запросы с ранее выданным токеном. Роли Keycloak здесь только отображаются. A11 добавляет отдельную область по трём процессам с ревизией и аудитом: она сужает права роли на карточки и отчёты, а прежние выгрузки недоступного процесса нельзя скачать. A12 ограничивает доступ к конкретным организациям и компаниям-плательщикам: карточки, назначения, отчёты и старые выгрузки повторно проверяются сервером. Администратор выбирает организации по названию в отдельном поиске; управление ролями Keycloak ещё не реализовано.

**Решение B01:** для исходного статического HTML-макета выбран один TypeScript API на Fastify и Drizzle ORM: они дают типизированный сервер и транзакции без второго backend-языка. UI использует React и Vite; точные версии зависимостей закреплены в `package-lock.json`. Локальный Keycloak 26.3 и PostgreSQL 17 запускаются изолированными Compose-сервисами. Ограничение: это стартовые workflow и локальные учётные записи, а не утверждённая production-схема или подключение к системам заказчика.

## Публичная демо-заявка

`/request/` — отдельная одноэкранная форма для судейского демо: заявка вуза, B2B или физлица. В форме используются только вымышленные данные; успешная отправка создаёт синтетическую активность в демо CRM. Вуз и компания получают связанные организации (`university`/`company`), физлицо — контакт без организации. API сохраняет honeypot, ограничение частоты, ключ идемпотентности и дедупликацию одинаковой формы; дополнительная схема для B2B не нужна, потому что существующая БД уже поддерживает тип `corporate` и организации компаний. См. [инструкцию публичного демо](deploy/public-demo/README.md).

## Запуск

Требуются Node.js 20.19+ (или 22.12+) и Docker с Compose. Папка `crm/` собирается самостоятельно: соседний каталог `design/` для запуска не нужен. Из папки проекта выполните одну команду:

```sh
./run-local.sh
```

Первый запуск создаёт закрытый файл `crm/.env.local` со случайными локальными паролями, поднимает PostgreSQL и Keycloak, применяет миграцию, создаёт тестовые аккаунты и запускает API/UI. Не добавляйте `.env.local` в Git и не копируйте эти пароли в другие среды.
Если UI, API или локальные CMS/LMS mock уже занимают свои порты, скрипт остановится с перечнем конфликтов до запуска второго экземпляра. Используйте уже открытый стенд или завершите его процесс перед повторным запуском; адрес UI не будет молча изменён на соседний порт.
Штатный запуск явно закрепляет адреса API, Keycloak и CMS/LMS mock на локальной машине; Vite читает конфигурацию `web/vite.config.ts` и не выбирает соседний порт, если `5173` занят. Для этого локального режима не нужны внешние CDN, MCP или облачные модели. Установка npm-пакетов при первом запуске всё ещё может требовать доступа к реестру пакетов, если зависимости не закэшированы.

- UI: <http://localhost:5173>
- API и краткая документация: <http://localhost:3001/docs>
- OpenAPI: <http://localhost:3001/openapi.json>
- Keycloak: <http://localhost:18080>
- CMS mock: <http://localhost:3101/health>
- LMS mock: <http://localhost:3102/health>
- Входы КАМ: `kam.anna`, `kam.dmitry`; руководитель: `manager`; администратор: `admin`. Случайные пароли находятся локально в `.env.local`.

### Отдельный режим для `lctcrm_demo`

Чтобы открыть изолированную синтетическую базу рядом с уже работающим стендом, сначала запустите PostgreSQL и Keycloak из обычного локального стенда и подготовьте `lctcrm_demo` через `node scripts/seed-synthetic-demo.mjs --apply-local-demo` (сначала можно проверить план командой `node scripts/seed-synthetic-demo.mjs --dry-run`). Это отдельная база; seed сопоставляет существующие QA-аккаунты по точным именам с их фактическими локальными Keycloak ID.

Добавьте redirect URI для второго адреса в локальный Keycloak, затем запустите приложение:

```sh
./scripts/configure-demo-local-keycloak.sh
./run-demo-local.sh
```

Первый скрипт идемпотентно добавляет `http://localhost:5174/*` и origin `http://localhost:5174` клиенту `lct-web`, сохраняя существующие redirect URI, включая адрес `5173`. Второй запускает UI на `5174`, API на `3003`, а CMS/LMS mock на `3103` и `3104`. API требует loopback PostgreSQL URL с базой `lctcrm_demo` и проверяет комментарий-маркер, который ставит seed script; при любом несовпадении API не запускается. Задания не применяют миграции и не пересеивают базу.

Импортируемые файлы, документы, отчёты и состояние CMS/LMS mock сохраняются отдельно в `.local-storage/demo/`. CORS UI и API настроены на origin `5174`; API принимает токены прежнего локального Keycloak. Проверить запуск можно по `http://localhost:3003/health` (ожидается `{"status":"ok","service":"crm-api"}`), `http://localhost:3103/health` и `http://localhost:3104/health`, затем открыть <http://localhost:5174> и войти имеющейся QA-учётной записью. Остановка demo через `Ctrl+C` не останавливает обычный UI/API на `5173/3001`.

Данные приложения находятся в Docker volume `lct-crm-postgres` и сохраняются между перезапусками. Чтобы удалить demo-базу, остановите контейнеры и отдельно удалите этот volume. Команда этого не делает.

Для будущего отдельного HTTPS-стенда скрипт `WEB_ORIGIN=https://<адрес CRM> KEYCLOAK_PUBLIC_ORIGIN=https://<адрес входа> node scripts/build-public-realm.mjs` создаёт игнорируемую конфигурацию Keycloak в `.local-storage/public-realm/`: только HTTPS, один адрес возврата, без direct grant. Он не меняет работающий локальный realm и не публикует приложение. Для реальной публикации ещё нужны отдельные DNS/TLS, reverse proxy с корректными заголовками и запуск Keycloak в production-режиме по [официальному руководству](https://www.keycloak.org/server/reverseproxy), а затем сквозная проверка входа; текущий `infra/docker-compose.yml` остаётся только локальным `start-dev`.

Фронтенд для такого окружения собирается отдельной командой `npm run build:public` при заданных `WEB_ORIGIN`, `VITE_API_URL`, `VITE_KEYCLOAK_URL` и `KEYCLOAK_PUBLIC_ORIGIN`. Команда требует три разных HTTPS-адреса без завершающего `/` и совпадение адреса входа в двух настройках; затем проверяет, что готовый JS содержит заданные адреса API и входа без локальных адресов сервисов. Она не запускает сервер и не подтверждает действительный сертификат. Обычный `npm run build` остаётся локальным. Предложенная схема для домена владельца: `crm.futura.team` (Web), `api.crm.futura.team` (API), `auth.crm.futura.team` (вход). Эти адреса пока проверены только как конфигурация, без DNS/VPS/TLS.

## Проверка за пять минут

1. Откройте <http://localhost:5173> и войдите как `kam.anna` с локальным паролем `KAM_ANNA_PASSWORD` из `.env.local`.
2. Создайте активности «Вуз», «Физлицо» без организации и «Компания». Для одной из них выберите ИТ-продукт и учебную программу из разных списков; в карточке проверьте обе связи.
3. В вузовской активности добавьте задачу со сроком, запишите итог контакта и отдельно подтвердите разрешённый переход. История покажет три отдельных действия; выполнение задачи само по себе стадию не меняет.
4. В «Отчётах» выберите учебную программу, постройте срез и создайте CSV или XLSX. Табличный файл содержит колонку «Учебные программы»; при нескольких программах одной активности места и факты LMS не складываются по программам.
5. Вернитесь в очередь, выберите сегмент «Компании» и подборку «Без следующего шага», обновите страницу и проверьте сохранение фильтров. Войдите как `kam.dmitry`: карточки Анны ему недоступны. Руководитель `manager` видит командный портфель; технический `admin` управляет схемой и доступом без автоматического доступа к бизнес-карточкам.

Для нового пакета: в карточке задачи раскройте «Обновления и подписка», подпишитесь как руководитель, затем запишите обновление или завершите задачу как КАМ. Руководитель увидит событие в «Уведомлениях» и ленте «Движение команды»; фильтр по КАМ сузит ленту. КАМ видит «Мои действия» и свой дашборд. Переключатель ☾/☀ находится в верхней панели. CSV можно загрузить в «Импорт и каталоги» и выбрать как формат готового отчёта; для CSV-заявок обязателен внешний ключ.

Реальные данные заказчика на стенде не используются. Текущий портфель — ограниченный срез CRM-активностей, а не полный дизайн Gate B.

## Быстрый сценарий проверки

1. Выполните `./run-local.sh`, возьмите сгенерированный пароль `kam.anna` из локального `.env.local` и войдите через Keycloak.
2. Создайте вузовскую активность с двумя продуктами, поставьте задачу на сегодня, запишите итог контакта и отдельно подтвердите предложенный переход стадии. В истории появятся независимые записи; выполненная задача сама стадию не меняет.
3. Создайте вторую активность для того же вуза, затем индивидуальную без организации (с компанией-плательщиком) и корпоративную. В корпоративной карточке раскройте «План программы», выберите адаптацию или новую программу и сохраните бриф, оценку методолога и объём работ.
4. Переключите сегмент и рабочую подборку, обновите страницу, вернитесь из карточки: очередь сохранит фильтр и позицию. Выйдите и войдите как `kam.dmitry`: карточки Анны в его очереди и каталоге нет.
5. Во втором терминале выполните `npm test` и `npm run test:db`; PostgreSQL-сценарий отдельно проверяет прямой запрос КАМ Б к записям КАМ А и запрет на повторное использование чужих связей.

## B01: контракт и границы

Сущности: `Organization` (вуз или компания), `Person`, `Activity` (независимый процесс и стадия), `Product`, `Task`, `ActivityEvent`, стадии и разрешённые переходы схем. Для физлица организация необязательна; организация-плательщик хранится отдельно. Несколько продуктов связываются с одной активностью. Стартовые стадии и переходы заданы миграцией как три отдельные схемы.

| Метод и путь | Действие | Право |
| --- | --- | --- |
| `GET /api/activities?segment=&collection=&offset=&limit=` | Страница очереди с точным общим числом и независимыми фильтрами | КАМ видит своё; руководитель — портфель |
| `GET /api/activities?ownerSub=` | Точная выборка по ответственному | Только руководитель; иначе `403` |
| `GET /api/activities?productId=` | Точная выборка по связанному продукту | В пределах области роли; КАМ видит только своё |
| `POST /api/activities` | Создать ручную активность одного из трёх типов | КАМ, руководитель; external origin и его метаданные отклоняются с `400` |
| `GET /api/activities/:id` | Карточка и действия | Сервер проверяет область; чужая запись выглядит как 404 |
| `PUT /api/activities/:id/details` | Уточнить контакт, несколько продуктов и приоритет по `expectedRevision`; можно добавить новое контактное лицо | КАМ/руководитель в области открытой активности; изменение в истории, стадия не меняется |
| `POST /api/activities/:id/tasks` | Создать задачу со сроком | КАМ, руководитель |
| `POST /api/activities/:id/outcomes` | Записать исход контакта и автора в историю | КАМ, руководитель; стадия не меняется |
| `POST /api/activities/:id/transition` | Выполнить запрошенный допустимый переход | КАМ, руководитель; переход сверяется с БД |
| `POST /api/activities/:id/tasks/:taskId/complete` | Отметить только задачу | КАМ, руководитель; стадия не меняется |
| `GET /api/activities/:id/history` | Прочитать историю | Сервер проверяет область |
| `GET /api/workflow`, `GET /api/catalog` | Стадии, переходы, клиенты и продукты | Вошедший участник CRM |
| `GET /api/guidance/:kind/:stageKey` | Инструкция только для стадии из текущего workflow | Вошедший участник CRM |
| `GET /api/activities/:id/guidance` | Инструкция и одна рекомендация с причиной из стадии и задач активности | Сервер сначала проверяет область активности |
| `GET /api/manager/kams` | Действующие КАМ для назначения | Только руководитель |
| `POST /api/manager/activities/:id/reassignment/preview` | Показать последствия смены КАМ без переноса | Только руководитель; проверка владельца и ревизии |
| `POST /api/manager/activities/:id/reassignment/confirm` | Передать активность и открытые задачи по одноразовому предпросмотру | Только руководитель; проверка текущей области и запись аудита |

Роли извлекаются сервером из подписанного Keycloak JWT после проверки issuer, аудитории `aud=lct-web`, клиента `azp=lct-web` и ключа JWKS. UI не может переключить роль или передать owner другого пользователя. КАМ получает 404 при прямом запросе чужой активности. Вход требует одной из ролей `kam`, `manager`, `admin`.

Роль `admin` сама по себе даёт технические экраны обменов, обезличенную сводку импорта, редактор вузовской схемы, публикацию инструкций и управление доступом известных пользователей; бизнес-очередь, контакты, подтверждение импорта и отчёты требуют `kam` или `manager`. Совмещённая `manager+admin` сохраняет командную область. Ответы технического монитора без роли руководителя скрывают бизнес-содержимое. При обновлении токена интерфейс пересобирает навигацию и очищает данные прежней области; сервер повторно проверяет роль и текущую область на каждом запросе. CRM умеет включать/отключать доступ и задавать сегментную/организационную область, но не создаёт аккаунты и не меняет роли в Keycloak.

На момент первого пакета B01 не было графиков, редактора схем, импорта, внешнего обмена и пользовательских вложений. Их текущее состояние описано ниже в разделах последующих пакетов и обновления A17.

Текущая карточка позволяет дополнить ранее неполное обращение: выбрать существующее или создать новое контактное лицо, изменить набор продуктов и приоритет без смены стадии. Новое контактное лицо не создаёт учётную запись CRM. При уходе из карточки с изменённым брифом, пунктом партнёрства, договорными данными или черновиком итога интерфейс предупреждает о несохранённом вводе. Список этапов в карточке не изображает переходы: допустимые переходы показаны отдельно по текущей серверной схеме.

## B02: инструкции и контекстная подсказка

Тексты всех 15 стадий B01 находятся в одном типизированном локальном модуле API. Оба endpoint сверяют стадию с текущим workflow при каждом запросе. Если схема больше не содержит указанную стадию, API не выдаёт старую инструкцию; если стадия существует, но для неё нет текста, API возвращает `409 guidance_unavailable`.

Контекстная рекомендация выбирается по доступным фактам в таком порядке: самое раннее просроченное открытое действие, ближайшее открытое действие, затем предложение для текущей стадии, когда открытых действий нет. Ответ содержит одну рекомендацию и отдельное объяснение `whyNow`; выполненные задачи не участвуют. Карточка показывает рекомендацию кратко и раскрывает полный текст по запросу.

На этапе B02 справка была локальным предварительным текстом (`provisional`) без редактора. Обновление A17 добавило черновики, публикацию по ролям и проверку связи с текущей стадией; опубликованные статьи всё ещё не являются подтверждёнными инструкциями заказчика. Контекстная рекомендация рассчитывается локальными правилами из текущей стадии и открытых задач.

## B03: портфель команды

Руководитель видит пункт «Портфель» и стартует с обзора команды. Чисто технические роли администратора и КАМ этого пункта не видят; прямой запрос `GET /api/manager/overview` без роли руководителя получает `403`. В обзоре есть общее число открытых активностей CRM, разрез по вузам/компаниям/физлицам, просроченные действия, зафиксированное ожидание ответа, активности без открытой задачи, нагрузка по КАМ и продукты, связанные с открытыми активностями.

API считает весь доступный руководителю портфель одним запросом и возвращает время среза `asOf` вместе с определениями каждого показателя. Просроченной считается открытая активность, у которой самая ранняя открытая задача уже просрочена; она считается один раз, даже если открытых задач несколько. «Без следующего шага» означает отсутствие открытых задач. В продуктовой разбивке одна активность учитывается один раз для каждого связанного продукта. Сегменты и проблемные числа открывают соответствующий фильтр очереди, а КАМ и продукты — точные выборки по ним.

Очередь загружается страницами по 50 записей (API допускает до 100 за страницу) и передаёт точный `total` для всех выбранных фильтров; кнопка «Показать ещё» позволяет пройти весь результат без лимита в 250 строк. Строка КАМ и продукт в портфеле открывают точную выборку по `ownerSub` или `productId`; очередь показывает активный фильтр и действие сброса. Фильтр продукта остаётся в пределах собственной области КАМ. Фильтр «Сегодня · МСК» использует календарный день `Europe/Moscow` независимо от системного часового пояса браузера. Если у нескольких записей один `ownerSub`, счётчики объединяются по этому стабильному ключу, а подпись берётся из самой недавно обновлённой открытой активности с разрешением совпадений по ID.

Это показатели только о записях и задачах CRM. Они не описывают продажи, заявки на обучение, слушателей, результаты обучения или платежи. Миграция `0002_b03_open_tasks_index.sql` добавляет частичный индекс для быстрой выборки ближайшей открытой задачи; существующая схема данных не меняется.

## B04: пункты партнёрства с вузом

В карточке вуза есть отдельный сворачиваемый список U01–U13 с состояниями «Не записан», «В работе», «Ожидание», «Зафиксировано в CRM» и «Не применяется». В списке группы раскрываются по запросу, а редактируется один пункт за раз. Отсутствующая запись в новой таблице читается как `unrecorded` версии 0: стадия активности, существующая история и закрытые активности миграцией не переписываются. Закрытые карточки остаются доступными только для чтения.

U14 — обзор, а не шаг после U13. Он показывает реальные открытые задачи активности, последнее событие истории и счётчики состояний U01–U13. Действия по пунктам создают неизменяемое событие в общей истории и требуют текущую версию; при конфликте API отвечает `409`, чтобы пользователь перечитал данные. Специальное действие возврата U05 доступно после того, как U04 отмечен как ожидающий или зафиксированный в CRM. Одна транзакция записывает U05 и возвращает U04 в работу, не меняя макроэтап.

«Зафиксировано в CRM» означает наличие записи координации в CRM, а не выполнение операции или внешний факт. Для U04, U06–U07 и U09–U13 нужны ссылка/позиция и источник; для других документированных пунктов — заметка или ссылка. U09, U11 и U13 не подтверждают прохождение обучения или проведение занятий без внешнего источника. Время фактического наблюдения во внешней системе отдельно не хранится. Статус подписания в CRM не является юридическим подтверждением; загрузки, отправка документов и интеграции с LMS или календарём в этот пакет не входят. Миграция `0003_b04_university_steps.sql` добавляется после `0001` и `0002` и хранит общий справочник U01–U13 отдельно от `stage_key`.

| Метод и путь | Действие | Право |
| --- | --- | --- |
| `GET /api/activities/:id/university-steps` | U01–U13 со статусом, заметкой, источником, автором и версией; сводка U14 | В области активности; для закрытой записи чтение доступно |
| `PUT /api/activities/:id/university-steps/:stepId` | Обновить одно состояние с `expectedRevision` | КАМ, руководитель; закрытые записи не принимают запись |
| `POST /api/activities/:id/university-steps/correction-return` | Атомарно записать U05 и открыть U04 заново | КАМ, руководитель; только после обмена документов |

U05 — необязательный пункт. Общий метод может только отметить его неприменимым; активную корректировку записывает отдельный возврат после применимого состояния обмена документами. Возврат сохраняет прежнюю заметку и источник U04, записывает новую информацию о корректировке в U05 и истории, и не меняет текущую стадию `stage_key`.

## A07–A09: администрирование схемы вузов

Администратор управляет одной общей схемой партнёрства для всех вузовских активностей: переименовывает стадию, удаляет её с явным переносом на сохранённую соседнюю стадию и настраивает переходы. Предпросмотр показывает весь затронутый портфель и блокировки; применение требует подтверждения и актуальных ревизии и токена предпросмотра. Перенос стадий, обновление схемы и события истории выполняются в одной транзакции. Закрытость и история активностей сохраняются; корпоративные и индивидуальные маршруты не меняются. Схема — локальная конфигурация демонстрационного CRM, а не согласованный процесс заказчика.

Новый переход вузовской активности требует `expectedWorkflowRevision` из карточки. API проверяет эту ревизию вместе с ожидаемой текущей стадией и разрешённым переходом; если администратор успел изменить схему, запрос получает `409` и карточку нужно обновить. Применение схемы также отклоняется при устаревшем предпросмотре или блокировке.

| Метод и путь | Действие | Право |
| --- | --- | --- |
| `GET /api/admin/workflow/university` | Прочитать общую схему и её ревизию | Только администратор |
| `POST /api/admin/workflow/university/preview` | Проверить изменение, показать переносы и блокировки без записи | Только администратор |
| `POST /api/admin/workflow/university/apply` | Атомарно сохранить схему и перенести затронутые вузовские активности по подтверждённому предпросмотру | Только администратор |

## B05: индивидуальное обучение и готовый внешний заказ

Обычный `POST /api/activities` создаёт только ручные активности; API и прямой вызов PostgresRepository отклоняют с `400` любой другой origin и любые поля внешнего происхождения. Индивидуальная внешняя заявка получает `external_ready` только после загрузки, настройки предпросмотра и подтверждения выбранных строк через серверный импорт `individual_applications`. Применение записывает источник, внешний ключ, файл, строку, сопоставление, хэш данных и автора в provenance, а также фиксирует импортированную активность на стадии `lms_handoff` в истории. Имя источника и содержимое файла пользовательские, поэтому запись отражает проверенный пользователем импортный маршрут и его аудит, а не криптографическое подтверждение внешней системы. Импорт пропускает ручные стадии продажи и не создаёт задачу, исход контакта, зачисление или факт начала обучения.

Маршрут новых индивидуальных активностей версии `v2`: `request` → `consultation` → `conditions` → `lms_handoff`; передача может продолжиться прямо к `result` либо пройти через `exceptions`. Возврат из исключений может вернуться к `lms_handoff`. Юридическое лицо-плательщик остаётся отдельной связью и не переводит индивидуальную активность в корпоративную. Существующие активности остаются на серверной версии `legacy`, где из `consultation` доступна прежняя стадия `enrollment`, а далее сохраняется путь `learning` → `closed`. Их стадия, история, задачи и закрытие не переписываются. `GET /api/activities/:id` возвращает `routeVersion` и `allowedNext` для этой активности; интерфейс строит переходы только из этого списка, а `GET /api/workflow` публикует отдельные переходы по версии. Миграции `0005_b05_restore_individual_legacy_order.sql` и `0006_b05_versioned_individual_routes.sql` сохраняют порядковые номера старых стадий и возвращают старый переход для уже существующих записей. Миграция `0007_b05_tag_preversion_individual_rows.sql` относит данные раннего B05-среза к v2 по сохранённому источнику или новому ключу стадии, оставляя исходные B01-записи на legacy-маршруте.

`GET /api/activities/:id/learning-facts` возвращает read-only проекцию LMS: тип внешнего факта, источник, время факта и ссылочный ключ. В таблице `individual_learning_facts` нет копий уроков, оценок, сертификатов или прогресса и нет CRM-метода бизнес-записи: локальный LMS mock передаёт проверяемые события, которые CRM сохраняет как проекцию. Реальная LMS заказчика не подключена. Текущий локальный обмен дедуплицирует внешние события по их ключам и проверяет связь с запросом; будущий реальный источник должен передавать только непрозрачные ключи без контактов, токенов или секретов.

## B06: корпоративный план программы

В основной колонке корпоративной карточки есть компактный сворачиваемый блок для специалистов. Он различает готовую программу, адаптацию, новую разработку и пока не определённый вариант. Запрошенное число мест хранится как плановое поле и не создаёт зачисления, участников или учебные факты в LMS. Ветки адаптации и новой программы содержат краткий структурированный бриф, методолога и оценку реализуемости, предложенные и согласованные объём, даты и критерии приёмки, а также состояние согласования со ссылкой и источником подтверждения. При смене варианта данные разработки сохраняются: для другого варианта они помечены как неактивные и остаются доступными для просмотра и редактирования.

Сохранение выдаёт следующую ревизию плана и добавляет в историю полный снимок до/после с автором и временем. Одновременная правка со старой ревизией получает `409`; закрытые активности остаются доступными для чтения. Для старых корпоративных активностей отсутствие строки плана читается как `undecided`, ревизия 0: миграция `0008_b06_corporate_plans.sql` не меняет их стадию, маршрут, историю или существующие записи. Состояния «одобрено/отклонено» требуют источник и ссылку/позицию evidence, но это запись в CRM, не самостоятельное юридическое подтверждение.

| Метод и путь | Действие | Право |
| --- | --- | --- |
| `GET /api/activities/:id/corporate-plan` | Прочитать план и ревизию; отсутствие записи возвращает `undecided` версии 0 | В области активности, включая чтение закрытой карточки |
| `PUT /api/activities/:id/corporate-plan` | Полностью сохранить структурированный план с `expectedRevision` и событием аудита | КАМ, руководитель; только открытая корпоративная активность |

План применим только к корпоративным активностям. Сервер возвращает `404` для скрытой по области записи, `409` для другого типа активности, закрытой карточки или устаревшей ревизии. Стадия активности не меняется при редактировании плана.

| Метод и путь | Действие | Право |
| --- | --- | --- |
| `POST /api/activities` | Создать ручное физлицо без организации на стадии `request`; внешний origin и metadata отвергаются | КАМ, руководитель |
| `POST /api/imports` → `PUT /api/imports/:id/preview` → `POST /api/imports/:id/confirm` с `target=individual_applications` | Создать выбранную внешнюю заявку после предпросмотра и подтверждения; активность начинается на `lms_handoff`, происхождение сохраняется в аудите импорта | Создатель предпросмотра с индивидуальной областью |
| `GET /api/activities/:id/learning-facts` | Читать LMS-проекцию `factKind`, `source`, `occurredAt`, `reference` | В области активности; чужая запись возвращает `404` |

## B07: вложения в активности

В карточке любого типа активности есть одна общая компактная карточка документов. Она показывает имя, размер, время и автора загрузки; разрешённые файлы скачиваются с авторизацией. Загрузка ограничена 20 MiB на файл и форматами PNG, JPEG, PDF, ZIP, GZIP (`.gz`/`.gzip`), RAR, DOC, DOCX, XLS и XLSX. Сервер проверяет имя, расширение и сигнатуру/структуру файла, а не доверяет MIME-заголовку. ZIP/GZIP и Office package validation выполняются в памяти с общим лимитом распакованных данных 20 MiB; архивные файлы не сохраняются в распакованном виде и не запускаются.

По умолчанию содержимое лежит в приватном каталоге `crm/.local-storage/documents` с правами каталога `0700` и файлов `0600`; для постоянного серверного размещения задайте `CRM_DOCUMENT_STORAGE` на приватный постоянный bind/volume. В PostgreSQL хранятся метаданные, SHA-256, владелец загрузки и события загрузки/успешного скачивания. Список и скачивание повторно проверяют область активности; после смены КАМ старый владелец получает `404`. Скачивание всегда идёт как `application/octet-stream` с `Content-Disposition: attachment`, `nosniff` и `no-store`.

| Метод и путь | Действие | Право |
| --- | --- | --- |
| `GET /api/activities/:id/documents` | Метаданные вложений активности | КАМ в своей области; руководитель — портфель; скрытая активность даёт `404` |
| `POST /api/activities/:id/documents?filename=...` | Передать тело `application/octet-stream` и сохранить проверенный файл | КАМ, руководитель; только открытая активность |
| `GET /api/activities/:id/documents/:documentId` | Повторно проверить права, записать событие и выдать файл как вложение | Та же текущая область доступа; скрытый файл даёт `404` |

Локальная файловая система сохраняет документы при перезапуске процесса на том же диске, но не синхронизирует их между серверами. Объектное хранилище, регулярная атомарная копия БД и файлов, антивирусная проверка и шифрование содержимого на уровне приложения пока не настроены; есть отдельная локальная проверка копирования и восстановления файлов ниже, без общей точки согласованности с БД.

## B08: проверяемый импорт данных

Руководитель загружает и подтверждает файлы в своей области. В существующем разделе «Состояние системы» администратор видит обезличенную сводку импорта: состояния заданий и количество строк, требующих разбора. API `GET /api/admin/imports/summary` отдаёт не более 20 последних заданий без исходных строк, имён, контактов и названий файлов; администратор без бизнес-роли не получает право подтверждать импорт.

Раздел «Каталоги и импорт» принимает настоящие книги Excel XLS/XLSX для контактов и поставщиков, а для внешних индивидуальных заявок — JSON-массив или объект `{ "applications": [...] }`. В JSON допускаются `null`-элементы: они показываются как пропущенные с предупреждением, сохраняя исходные номера последующих записей. Таблица XLS/XLSX должна содержать заголовок в выбранной строке; для заявок используются ключи `applicationId` (обязательный стабильный внешний ID), `applicant.fullName`, `applicant.email`, `applicant.phone` и `productName`. Вложенные объекты JSON раскрываются в колонки с точечной нотацией. Контакты сопоставляются с `externalKey`, `fullName`, `email`, `phone`, `organizationName`; поставщики — с `externalKey`, `name`, `productNames` (названия нескольких продуктов разделяются точкой с запятой или новой строкой). Для XLS/XLSX UI может прочитать строку заголовка по любому номеру строки листа. Примеры заголовков подставляют начальное сопоставление, которое пользователь проверяет и может изменить. Исходные заголовки и строки сохраняются без нормализации; email и строковые телефоны сохраняют исходное написание и регистр.

Файл ограничен 5 MiB, таблица — 2 000 строк данных, 100 колонок и 12 листов. Парсер SheetJS Community Edition 0.20.3 (Apache-2.0; официальный пакет [SheetJS](https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz)) читает оба формата Excel, в том числе legacy XLS. Формулы и ячейки со ссылками не переносятся, не исполняются и не открываются. Превью не меняет бизнес-данные: сервер показывает ошибки по строкам, предупреждения о вероятных совпадениях и причины совпадения по имени/email/телефону; такие совпадения никогда не объединяются автоматически. Идентификатор импорта общий для пространства ключей `(цель, источник, внешний ID)`: совпадение чужого ключа безопасно блокируется и показывается как строка конфликта, не раскрывая чужую запись. Его разбирают с владельцем источника; UI не даёт принудительно присвоить ключ. Повтор внешнего ключа в том же источнике обновляет свою импортированную запись, если payload не изменился; изменённые данные требуют отдельного просмотра и подтверждения. Одинаковые бесключевые записи внутри одного файла отмечаются как повтор, и сохраняется только первая. Без внешнего ID повторная загрузка отдельного файла может создать отдельную запись.

Каждый импорт и список кандидатов доступны только загрузившему пользователю; административная роль сама по себе не открывает его персональные данные. Внешние заявки создают личную CRM-активность на `lms_handoff`; состояние платежа остаётся `unknown`, и импорт не создаёт платежи, задачи, зачисления или учебные факты. Поставщики хранятся отдельно от организаций-покупателей и связываются с продуктами каталога. Подтверждение связано с ревизией предпросмотра и ключом идемпотентности, сохраняет кумулятивные построчные результаты и позволяет повторить неудачные строки, не теряя ранее обработанные. При обновлении меняются только сопоставленные поля; несопоставленные сохраняются, пустая ячейка в сопоставленном необязательном поле очищает его. После импорта обновляются очередь, каталог, список контактов и доступный текущему пользователю портфель. В provenance фиксируются источник, внешний ключ, непрозрачная ссылка на файл/задание, номер строки, заголовки, сопоставление, хеш данных и результат.

Загруженный исходный файл кратковременно записывается в `crm/.local-storage/imports` (каталог `0700`, файл `0600`) и удаляется после чтения. Извлечённый предпросмотр с исходными значениями в PostgreSQL имеет срок действия 24 часа; он привязан к создателю. Вкладка хранит только ссылку на задание и ограниченные выборы импорта: после перезагрузки она перечитывает предпросмотр через API с проверкой прав, не повторяя подтверждение автоматически. Этот путь ещё не проверен в браузере. Очистка выполняется при старте и затем ежечасно, поэтому при работающем API удаление может задержаться до часа после истечения срока; при выключенном API — до его следующего запуска. Задание и результаты подтверждения удаляются через 7 дней. Provenance сохраняется отдельно как аудит: содержит непрозрачную ссылку на файл/задание, внешний ключ, заголовки, сопоставление, хеш, автора и действие, но не исходные значения ячеек; автоматический срок хранения этой аудиторской метадаты пока не настроен. Долговременное хранение исходных файлов и импортированных исходных строк не включено.

Реальные исходные файлы `User Uploads`, `Vendors` или внешних заявок в этом рабочем задании не были предоставлены, поэтому проверены только сгенерированные файлы XLS/XLSX и описанный JSON-контракт, а не фактические клиентские шаблоны.

| Метод и путь | Действие | Право |
| --- | --- | --- |
| `POST /api/imports?filename=...&target=...&source=...` | Загрузить файл для изолированного предпросмотра (`application/vnd.lct.import`) | Авторизованный пользователь |
| `GET /api/imports/:id` / `DELETE /api/imports/:id` | Прочитать или удалить свой предпросмотр | Только создатель |
| `PUT /api/imports/:id/preview` | Выбрать лист, строку заголовков и сопоставление; рассчитать проверки и совпадения | Только создатель |
| `POST /api/imports/:id/confirm` | Подтвердить выбранные строки указанной ревизии | Только создатель |
| `GET /api/contacts` / `GET /api/vendors` | Выбрать импортированные контакты и поставщиков в своей области | Только создатель/владелец области |

Миграция `0010_b08_imports.sql` добавляет отдельные каталоги поставщиков и связи продуктов, закрытые импорт-задания, внешние ключи идемпотентности и provenance; ранее созданные организации, активности, история и платежные/учебные данные не переинтерпретируются.

## B09: локальный двусторонний CMS/LMS обмен

`npm run dev` запускает CRM API/UI и два отдельных HTTP mock-процесса: CMS на `127.0.0.1:3101` и LMS на `127.0.0.1:3102`. Это единственный поддерживаемый режим B09: оба адреса API проверяются как HTTP loopback origins; удалённые и production endpoints не принимаются. Данные внешней стороны mock хранятся в игнорируемом каталоге `api/.mock-state/` и переживают перезапуск сервиса; настраиваемый `CRM_MOCK_STATE_DIR` позволяет задать другой локальный каталог. Контракт использует только синтетическое обращение и непрозрачные ссылки.

Четыре направления отображаются раздельно: CMS → CRM, CRM → CMS, CRM → LMS, LMS → CRM. В PostgreSQL сохраняются задания и входящие события с внешним event ID, correlation ID и idempotency key. Для заданий ключ ограничен активностью, повтор использует тот же ключ, а атомарный claim не даёт двум параллельным отправкам одновременно выполнить один запрос. Отправка, не получившая ответ в течение 30 секунд, становится доступной для безопасного повтора с тем же ключом; устаревший ответ не может перезаписать результат новой попытки. Повторы ограничены тремя отправками. CMS event, новая активность с `origin=CMS mock`/внешним ключом и входная проекция фиксируются одной транзакцией; повторная доставка восстанавливает неподтверждённый CRM → CMS ответ и не создаёт копию активности. LMS факты дедуплицируются по внешнему event ID; отдельные события одного запроса (например, зачисление и завершение) сохраняются независимо. Входной тип события и связь с принятым CRM запросом проверяются до проекции. Событие, пришедшее пока исходящий запрос ещё ждёт сетевого подтверждения, откладывается до следующего чтения, а не отклоняется навсегда.

Статусы описывают конкретный этап обмена: `sent` — HTTP запрос выполняется; `accepted` — mock подтвердил запрос; `performed` — CRM получил и записал связанное внешнее событие; `rejected` — mock явно отклонил действие; `retryable_error` — технический сбой. Принятый запрос не означает зачисление или завершение. Полученная CMS заявка до назначения доступна КАМ в короткой общей очереди без контактных данных; первый захват атомарно назначает владельца и записывает событие истории. После захвата доступ к карточке остаётся в области этого КАМ. Происхождение и внешний ключ видны в карточке. CMS получает `received` только после создания активности, а CRM показывает внешний ответ принятым только после ответа CMS mock.

| Поле или действие | Владелец в B09 mock-контракте | CRM поведение | Capabilities |
| --- | --- | --- | --- |
| Обращение с сайта и внешний ключ | CMS mock | Создаёт activity-проекцию с источником/ключом; не меняет CMS до ответа | `mock`: чтение и дедупликация поддержаны |
| CRM подтверждение получения обращения | CRM отправляет, CMS mock подтверждает | Внутреннее состояние отправлено/принято хранится отдельным заданием | `mock`: запись `received` поддержана |
| Запрос подготовки доступа | CRM инициирует, LMS mock решает о принятии | CRM хранит запрос и correlation; не меняет LMS зачисление | `mock`: отправка/принятие/отклонение поддержаны |
| Зачисление, начало и завершение обучения | LMS mock | Read-only проекция типа факта, источника, времени и ссылки после LMS event | `mock`: входные факты поддержаны; CRM запись запрещена |
| Курсы/содержимое, расписание, оценки, сертификаты, платежи | Не подтверждены и не выдаются mock | Не создаются и не симулируются в B09 | `unknown` / `not provided` |

Статус `mock` относится к локальному демонстрационному контракту, а не к реальным возможностям заказных CMS/LMS. Реальные API и их права здесь не настроены.

| Метод и путь | Действие | Право |
| --- | --- | --- |
| `GET /api/cms-mock/intake` | Краткая общая очередь новых CMS mock обращений без контактов | КАМ/руководитель |
| `POST /api/cms-mock/intake/:id/claim` | Назначить обращение текущему КАМ с записью в историю | КАМ; только пока обращение не назначено |
| `GET /api/activities/:id/exchanges` | Прочитать задания обмена конкретной активности | Только текущая область активности |
| `POST /api/activities/:id/exchanges/lms-requests` | Запросить подготовку доступа в LMS mock с ключом идемпотентности | КАМ/руководитель в области активности; открытая individual на `lms_handoff` |
| `POST /api/exchanges/:id/retry` | Повторить технически неудачное задание (не более трёх отправок) | Владелец связанной активности или руководитель с доступом; технический администратор повторяет только пакетный pull |
| `GET /api/admin/exchanges` | Очередь заданий и доступность локальных mock-сервисов | Только администратор |
| `POST /api/admin/exchanges/cms/pull`, `POST /api/admin/exchanges/lms/pull` | Получить mock-события и создать их read-only CRM-проекции | Только администратор |
| `POST /api/admin/exchanges/mocks/:system/fail-next` | Настроить однократную ошибку или отклонение для демонстрации | Только администратор |
| `POST /api/admin/exchanges/lms/:id/outcome` | Попросить LMS mock выполнить/отклонить принятый запрос | Только администратор; учебный факт возвращается отдельным LMS event |

Миграция `0011_b09_external_exchange.sql` добавляет `exchange_jobs` и `exchange_events`, сохраняя текущие activity/import contracts. `npm run db:migrate` применяет её вместе с предыдущими миграциями.

### Сценарий B09 в браузере

1. Войдите как `admin`, откройте «Состояние системы» и нажмите «Получить обращения». CMS mock вернёт синтетическое обращение; проверьте `CMS → CRM` и отдельную запись `CRM → CMS` со статусом ответа.
2. Войдите как `kam.anna`, откройте «Входящие с сайта» и нажмите «Взять в работу». Обращение появится в вашей области; карточка покажет происхождение и отдельно подтверждение CRM → CMS.
3. Загрузите синтетическую индивидуальную заявку через импорт, проверьте предпросмотр и подтвердите выбранную строку. Откройте созданную карточку на стадии «Передача в LMS», отправьте запрос и проверьте, что он отображается как «Принято источником», а факта зачисления ещё нет.
4. Войдите как `admin`, откройте «Состояние системы», в LMS mock выполните принятый запрос и выберите демонстрационный факт. После LMS → CRM обмена откройте ту же активность: факт появится в отдельной read-only проекции со ссылкой и временем.
5. Настройте «Сбой следующего запроса», отправьте новый запрос из подходящей индивидуальной активности и повторите задание после технической ошибки. Число попыток растёт, а статус переходит в принятое только после ответа LMS mock.

## Локальная проверка нагрузки

После обычного `./run-local.sh` выполните из каталога `crm`:

```sh
node scripts/load-test.mjs --confirm-local-only
```

Сценарий использует только локальные PostgreSQL и Keycloak, отдельную БД `lctcrm_load` и API на `127.0.0.1:3002`. Он создаёт 50 отдельных учётных записей `load.kam.*` с ролью КАМ, получает отдельный JWT для каждой, готовит синтетические активности через API и одновременно запускает 50 смешанных рабочих сессий и 10 заданий менеджерских XLSX-отчётов. Длительность и начальный объём набора можно задать флагами из `node scripts/load-test.mjs --help`; результат прогона — один JSON-объект в stdout.

Для ограниченной проверки seed-набора без timed load и отчётов выполните:

```sh
node scripts/load-test.mjs --confirm-local-only --seed-only
```

Режим использует те же `lctcrm_load`, 50 тестовых КАМ-сеансов и API на порту 3002, создаёт только недостающие seed-активности, затем перезапускает изолированный API и читает ту же активность из сохранённой базы. В JSON указываются число новых seed-строк и результат повторной проверки идемпотентности; секреты и токены не выводятся. Запустите команду дважды: во втором запуске `newSeedActivitiesThisRun` и `idempotenceNewSeedActivities` должны быть равны `0`.

Флаг `--confirm-local-only` обязателен. Существующая БД используется только при наличии отметки владельца harness; чужая БД, занятый порт 3002, чужие записи и аккаунты с тем же именем приводят к остановке без очистки. Созданная БД и тестовые учётные записи сохраняются для проверки результата; автоматического `DROP`, сброса данных и удаления пользователей нет. Повторный прогон повторно использует исходные активности и накапливает историю контактов, задач и отчётов. Отчётные файлы сохраняются в закрытом игнорируемом каталоге `crm/.local-storage/load-harness/reports` и удаляются стандартной очисткой по сроку хранения отчётов. Все тестовые данные синтетические, секреты читаются из игнорируемого `.env.local` и не попадают в JSON.

Прогон 28.09.2026 на локальном Mac arm64 (8 логических CPU, 16 GiB RAM, PostgreSQL 17.11) с накопленной синтетической БД: 50 разных KAM-сеансов, 1000 активностей, 60,04 секунды, 65 479 смешанных HTTP-запросов без ошибок. Время полного HTTP-ответа: min 6,14 мс, p50 43,13 мс, p95 63,71 мс, max 304,09 мс; 65 479/65 479 завершились не дольше 1 секунды. Десять XLSX-экспортов перекрывались по времени и скачались; формирование от POST до обнаруженного завершения заняло 0,91–6,30 с, скачивание — 0,06–0,09 с. До прогона БД уже содержала 24 511 задач и 74 612 событий после диагностических запусков; это не чистый dataset и не гарантия производительности другой машины. Полные измерения и размеры БД сохранены в игнорируемом `.agent/load-a15-result.json`.

### Локальная проверка резервной копии и восстановления

После создания синтетической БД `lctcrm_load` запустите из каталога `crm`:

```sh
node scripts/verify-backup-restore.mjs
```

Скрипт берёт пароль только из игнорируемого `.env.local`, проверяет отметку load harness и подключается строго к `127.0.0.1:54329`. Нужны установленные `pg_dump` и `pg_restore` версии не старше локального PostgreSQL; `pg_restore` не может быть старше `pg_dump`. Локально проверены клиент 18 и сервер 17. Резервная копия создаётся в `.agent/private` с правами `0600`; восстановление идёт в новую уникальную БД `lctcrm_restore_*`, а существующие БД не очищаются и не заменяются. Проверка сопоставляет количества строк во всех публичных таблицах и контрольные суммы записей и первичных ключей; выводит только имена БД, размеры, количества строк и SHA-256, без содержимого и секретов. Созданные backup-файл и восстановленная БД остаются для ручной проверки. Это копия PostgreSQL; внешние файлы вложений и отчётов в неё не входят.

Файлы проверяются отдельно, из каталога `crm` выполните `node scripts/verify-file-backup-restore.mjs`. Команда копирует документы, готовые отчёты и `cms.json`/`lms.json` локальных mock-сервисов в `.agent/private/file-backups`; отсутствующие каталоги или mock-файлы допустимы. Каталоги копии и тестового восстановления имеют права `0700`, файлы сохраняют исходный owner-only режим; проверяются SHA-256, размер и режим каждого файла, а restore создаётся рядом в отдельном каталоге без перезаписи источника. Временный импорт и `.local-storage/load-harness` исключены; пользовательские пути хранения принимаются только внутри `crm`. PostgreSQL и файловое состояние не образуют одну атомарную копию, поэтому между ними возможна разница по времени.

Совместный сценарий проверяется отдельно командой `node scripts/verify-joint-fixture-backup-restore.mjs`. Она создаёт временную синтетическую БД и несколько `.blob` в каталоге с правами `0700`, запрещает TCP у временного PostgreSQL и использует только приватный Unix socket. Пока fixture закрыта для записей, транзакция удерживает блокировки таблиц; `pg_dump` сохраняет её экспортированный snapshot, после чего те же файлы копируются в backup. Восстановление идёт в новую fixture-БД и отдельные каталоги, затем существующий `verify-private-blobs.mjs` проверяет ключи, размер и SHA-256 метаданных восстановленной БД и файлов. Скрипт не читает `.env.local`, CRM-базу, настроенные папки хранения или mock state и удаляет временный кластер после остановки. Проверка на синтетическом контуре прошла с разрешённым локальным доступом: восстановлены 2 документа и 1 отчёт, метаданные и SHA-256 совпали, временный каталог удалён. Это доказывает согласованность сценария при остановленных записях, но не создаёт атомарную копию работающего CRM.

Для сверки связности метаданных и файлов на **остановленной тестовой копии** запрос [private-blob-metadata.sql](scripts/private-blob-metadata.sql) выдаёт JSON с ключом, размером и SHA-256 всех документов и завершённых экспортов. Сохраните его в приватный файл с режимом `0600`, затем передайте в `node scripts/verify-private-blobs.mjs --metadata-file /absolute/private/metadata.json --documents-root /absolute/crm/.local-storage/documents --reports-root /absolute/crm/.local-storage/reports`. Проверяльщик требует явные локальные пути, не подключается к PostgreSQL, не изменяет файлы и выводит только агрегированные расхождения. Метаданные и папки должны относиться к одной согласованной копии; независимые снимки не доказывают восстановимость.

## B10–B12: готовые отчёты и файлы

Экран «Отчёты» открыт руководителю; серверный расчёт допускает также КАМ в области его активностей. Чисто техническая роль администратора не даёт доступ к бизнес-отчётам; совмещённая роль `manager+admin` сохраняет область руководителя. Активности, ограниченные владельцем импорта, остаются доступны только своему КАМ. Дата периода — дата создания активности по `Europe/Moscow`. Фильтры применяются до сохранения полного среза. PostgreSQL хранит метаданные в `report_jobs`, а каждую исходную строку — отдельно в `report_snapshot_rows` с устойчивым номером; метрики и график рассчитаны по всему набору в БД. Таблица API отдаёт по 25 строк за страницу и сообщает общий `rowCount`. Архитектурного порога в 20 000 строк нет.

Готовые отчёты:

- **Портфель CRM** считает каждую активность один раз и отдельно показывает открытые активности, просроченные активности и записанное состояние «Ожидаю ответа». Источники — активности, задачи и продуктовые связи CRM.
- **Спрос и факты обучения** оставляет корпоративные активности и заявленные места отдельной единицей, отдельно считает записанные LMS-события зачисления, начала и завершения. Если часть корпоративных планов не указывает число мест, сумма помечена как «известная часть» с долей заполнения. Входящие обращения, заявки на обучение, уникальные обучающиеся и параллельные потоки явно показываются как «Недостаточно данных», пока нет полного перечня исходных обращений и заявок, стабильного ID человека и периодов потоков. Это число событий в read-only проекции, не число уникальных людей. Период фильтрует дату создания активности; прикреплённые учебные факты берутся за всё доступное время. Полнота синхронизации LMS неизвестна, поэтому отсутствие фактов не трактуется как отсутствие обучения. Для каждого показателя доступны период и группировка; время последнего факта относится к соответствующему виду события. Для принятых LMS mock-событий CRM хранит время получения; оно показывается только если все факты данного вида в срезе связаны с принятыми событиями. Старые и прямые факты без такой связи оставляют время неизвестным, что отмечено в UI и выгрузке. Спрос можно смотреть по связанным продуктам: продуктовый график активности считает один раз в каждом продукте, а заявленное число мест полностью относится к каждому связанному продукту только для этого разреза. Если у активности несколько продуктов, значения разрезов пересекаются и их нельзя складывать; общий показатель мест считается один раз на активность. Связанный продукт не объявляется программой, курсом или потоком.

Оба отчёта указывают единицу, определение, источник, дату среза и границу полноты. Платежей, выручки, конверсии, месячной динамики и параллельных потоков отчёты не выдумывают: для них нет подтверждённых фактов или периодов. Ручной приоритет программы не влияет на статистику.

Фильтры, метрики, график, все страницы исходных строк и XLS/XLSX/PDF/JSON/PNG-выгрузка используют один транзакционно сохранённый as-of срез. Экспорт worker читает все его строки непосредственно из БД; он не зависит от открытой страницы UI. Нажатие на столбец строит отдельный фильтрованный snapshot, а кнопка в строке открывает ту же активность в CRM. До показа страницы, статуса и скачивания сервер проверяет актуальную область по каждому исходному activity ID и сверяет фактическое число строк с сохранённым rowCount; неполный или отозванный срез закрывается с ошибкой. Ответы отчётов получают `Cache-Control: private, no-store`. Экспорт выполняется последовательно в ограниченной фоновой очереди, состояние и ошибки сохраняются в PostgreSQL; runtime recovery повторно отправляет только задания `queued`, а возврат зависших `running` в очередь делается при старте процесса. Файлы хранятся в закрытом каталоге `.local-storage/reports`, целостность проверяется при скачивании. Snapshot продлевается вместе с ожидающей выгрузкой; live export удерживает строки исходного snapshot до своего истечения. По завершении общего 24-часового срока его строки удаляются. Неудачная очистка файла остаётся на повторную попытку, временные файлы старше суток удаляются при плановой очистке.

Для XLS, XLSX, PDF-отчёта и JSON можно раскрыть «Колонки выгрузки» и оставить только нужные поля. По умолчанию выбраны все прежние колонки. Выбор передаётся серверу и сохраняется в задании; он меняет только исходные строки файла, а полный snapshot, показатели, график и повторная проверка прав остаются прежними. Список и подписи allowlist возвращает `GET /api/reports/ready`; API отклоняет пустой, повторяющийся или неизвестный выбор. Графические PNG/PDF не используют выбор колонок.

JSON полного среза по умолчанию включает для каждой доступной активности ID самой записи, стадии и владельца, ID организации/контакта/плательщика, связанные продукты и учебные программы с ID, вариант корпоративной подготовки, ссылки по ID на документы и договорно-лицензионные записи. Это связи на момент среза, а не публичные URL или внутренние ключи файлового хранилища; скачивание документа по ID отдельно проверяет текущие права. Выбор сокращённого набора колонок сокращает и строки JSON. `programMode` описывает вариант корпоративной подготовки, а связанная учебная программа хранится отдельно и не приравнивается к продукту или потоку. Старые сохранённые срезы не обогащаются задним числом.

XLS/XLSX-файлы создаются через SheetJS в worker thread, PDF через PDFKit с встроенным Manrope, PNG через Sharp. Каждая выгрузка содержит маркировку `synthetic_demo` / «Синтетические данные». Строки, начинающиеся с управляющего знака формулы, экранируются в таблицах. Формат XLS ограничивает лист 65 536 строками, включая две строки заголовка отчёта: если все исходные записи не помещаются, API явно отклоняет экспорт и предлагает XLSX или JSON. XLSX также получает явный отказ выше 1 048 574 исходных строк на одном листе. Для XLS/XLSX/PDF/JSON проверяется общий размер исходных строк в PostgreSQL: предел 32 MiB обеспечивает безопасную сборку; API возвращает явную ошибку и предлагает сузить фильтры, строка не теряется молча. Worker загружает исходные строки в собственную рабочую нить с heap-пределом 512 MiB, поэтому сборка и синхронный рендер SheetJS не блокируют event loop Fastify; одновременно формируется один файл. Размер готового приватного файла ограничен 100 MiB. PDF использует шрифт из Manrope SIL Open Font License, указанной в `web/public/fonts/OFL-Manrope.txt`.

API: `GET /api/reports/ready`, `POST /api/reports/snapshots` (возвращает первую страницу и полный rowCount), `GET /api/reports/snapshots/:id?page=1` (страница по 25 строк), `POST /api/reports/exports` (необязательный массив B11 `columns`), `GET /api/reports/exports/:id` и `GET /api/reports/exports/:id/file`. Forward-миграция переносит старые строки snapshot из JSONB payload в `report_snapshot_rows`; новые задания сохраняют в JSONB только компактные метаданные. Полные схемы и ошибки доступны в OpenAPI.

### Обновления локального стенда после UX-проверки A17

Рабочая очередь ищет активности на сервере по названию, организации и контактному лицу в пределах текущих прав; запрос сохраняется при возврате из карточки. В карточке видны сохранённые контакты и несколько независимых договорно-лицензионных записей. Срок лицензии хранится с точностью даты, года или как неизвестный — год не превращается в фиктивный день. К записи можно привязать только приватный файл той же активности; изменения имеют ревизию и попадают в историю.

Недавние выгрузки отчётов доступны после повторного входа в раздел: `GET /api/reports/exports?limit=20` повторно проверяет доступ к каждому заданию. Фильтр из столбца графика показывается явно; обычное «Показать отчёт» очищает скрытые ограничения детализации. Справочник этапов доступен из меню и использует тот же источник, что подсказка карточки. Руководитель сохраняет черновик статьи, администратор публикует его для текущей стадии; при изменении схемы старый черновик требует повторной проверки, а устаревшая опубликованная статья не выводится как актуальная. Менеджер вручную создаёт задачу из подсказки, откладывает или отклоняет её с причиной и может скопировать черновик сообщения. Система ничего не отправляет клиенту автоматически.

Редактор общей вузовской схемы позволяет добавлять и переставлять стадии, менять переходы и предварительно просматривать затронутые активности перед применением. Это локальная CRM-реализация; CMS и LMS по-прежнему обозначенные симуляторы. Визуальная точность относительно Atomaro и работа на реальном телефоне требуют отдельной приёмки.

## Каталог учебных программ (A105)

В «Справочнике этапов» руководитель или администратор управляет компактным каталогом учебных программ: добавляет программу и задаёт ручной порядок показа 1–5 (1 — выше). Это не оценка спроса, не план продаж и не приоритет конкретной активности; значение сейчас влияет только на сортировку каталога. Q&A допускает ручное ранжирование со стороны КАМа **или** администратора; здесь выбран администратор и дополнительно руководитель, а КАМ сохраняет выбор уже существующих программ в карточке активности. `GET /api/programs` доступен КАМ для выбора, а `POST /api/programs` и `PUT /api/programs/:id/priority` требуют роли руководителя или администратора на сервере. Одна программа может относиться к нескольким активностям. Число связанных активностей ограничено областью просмотра пользователя; техническому администратору без бизнес-роли командная аналитика в UI не показывается. Ссылки карточки сохраняются через `PUT /api/activities/:id/details` с `programIds` и `expectedRevision`. Снимок отчёта фиксирует ID и название связанной программы на момент формирования и включает их в полный JSON; последующее переименование каталога не меняет уже созданный файл. Локальный стенд содержит иллюстративные записи из A108; реальные запуски программ заказчика этим не подтверждаются.

## Демонстрационный каталог (A108)

Создание активности предлагает шесть ИТ-продуктов: RT.DataLake (корпоративное хранилище данных), RT.Warehouse (позиция из присланного файла поставщиков, назначение не подтверждено), Базис (инфраструктура для DevOps), Аврора (мобильная платформа), RT.Web3Gate (распределённые реестры) и Акола (среда веб-разработки). Интерфейс раскрывает подтверждённое назначение там, где оно известно; внутренние имена сохранены для совместимости с импортом и историей. RT.Warehouse оставлен доступным, поскольку он явно есть в исходной книге поставщиков и нужен для корректного предпросмотра двух продуктов в одной ячейке. Отдельный каталог учебных программ содержит шесть кратких названий из листа «08 Программы» файла `ai-docs/RTK_CRM_Research_Registers.xlsx`: веб-разработка «Акола», DevOps/Базис для преподавателей, мобильная разработка на Авроре, распределённые реестры/RT.Web3Gate, анализ данных с low-code и управление ИТ-проектами. Это иллюстративные позиции локального стенда, не подтверждённый актуальный коммерческий прайс или факт запуска. Тестовые названия и старое общее «IT-школа: разработка» исключены из нового выбора; существующие связи с ними сохранены и в карточке помечаются как прежние позиции, которые можно снять. Форма создания запрашивает каталог при каждом открытии, чтобы старая вкладка не показывала устаревший список. Интеграционные тесты используют отдельную базу `lctcrm_integration` и больше не добавляют свои фикстуры в демонстрационный каталог.

В форме создания активности теперь можно сразу выбрать несколько учебных программ отдельно от нескольких ИТ-продуктов. `POST /api/activities` принимает `programIds`, проверяет наличие каждой программы в транзакции и записывает связи вместе с новой активностью; неизвестная программа отменяет создание целиком. В карточке оба набора остаются редактируемыми независимо. Табличные CSV/XLS/XLSX и PDF-выгрузки содержат названия связанных учебных программ из сохранённого среза; JSON дополнительно сохраняет их ID. Оба готовых отчёта можно ограничить одной учебной программой. Фильтр выбирает связанные активности CRM; если у активности несколько программ, её места и факты LMS не распределяются между ними и не должны суммироваться как независимые показатели программ. API также не разрешает добавить скрытый продукт к новой активности или заново привязать его после снятия; уже существующую связь можно сохранить или удалить. Интеграционные проверки хранят свои временные файлы отдельно от файлов демо-стенда.
